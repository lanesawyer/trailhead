# The control plane inside the server

> **Built (2026-11-07, TRAIL-1064 to TRAIL-1076; Lookout's side is TRAIL-1072).** Written as a proposal in TRAIL-838; Lane answered its open questions on 2026-11-07, and [Decisions](#decisions) records the answers. Each step under [Migration in steps](#migration-in-steps) says what was built and where it differs from the plan. The sections before it describe the design as proposed, so "today" there means before TRAIL-164. Facts are from the code at `56734a0`; what is still a guess is marked **Guess**. It touches Decided items in [overview.md](overview.md) and [state.md](state.md) only to carry them out ("the server is the control plane when the `factory` feature is on").

## Why

Today `trailhead-factory run` (crate `trailhead-factory-host`) is a second process beside `trailhead serve`. It opens the same SQLite file as a second `Store`, holds its own iroh endpoint, and forwards the daemons' API tunnel and Lookout's `trailhead/ui/0` streams to the server's loopback port. That costs:

- **Polling across processes.** The server's `Store::changes()` watch (bumped after each commit in the process) never fires for the factory, so `wake.rs` reads the events table every second (TRAIL-158). It is a 1-second timer and a second knob (`--poll-secs`) where the commit itself could wake the loop.
- **Two processes to keep up.** The CLI starts and restarts the server by itself; nothing starts or restarts the factory. `mise run install` can only warn about a stale one.
- **A hand-made lock.** `control.lock` stops two control planes on one machine (TRAIL-113); the server already has one-instance logic (`server.pid`, the `instance` id).
- **Two endpoints for Lookout.** Lookout dials the factory's iroh endpoint for everything, and when the factory is down it can't reach the server either, hence the "factory stopped" fallback to a loopback URL that is useless away from the machine.
- **A second set of files** (`status.json` loopback surface, bearer token, `ui-allowed`) next to the server's own.

## What moves where

| Today (`trailhead-factory-host`) | After | Notes |
| --- | --- | --- |
| Run loop, reconcile, merger, reviews, `Host`, `StatusBoard` (`trailhead-control`) | Unchanged crate, started by the server | One `Factory` per repo, as now. |
| `CoreTracker` over an `Arc<Store>` | Same, on the server's own store | `AppState.store` is a `Store` by value; it becomes `Arc<Store>` (small, mechanical). The tracker then needs no second SQLite connection pool. |
| `wake.rs` (poll the events table) | Deleted; run loops wait on `store.changes()` | See [Lifecycle](#lifecycle). |
| iroh endpoint, `trailhead/api/0` tunnel, daemon protocol (`RemoteDaemon`, `Peers`), `trailhead/ui/0` | Bound by the server's factory module | The API tunnel's target becomes the server's actual listen address (from the listener, not `--server`); `server_check` becomes unnecessary because the server is the process asking. |
| `surface.rs` loopback status port and `status.json` | Routes on the server (`GET /v1/factory/status`, `/events`) behind the normal bearer token | Retires a second token file and port. `status` and `logs --follow` become ordinary API clients. **Guess:** the iroh `{"op":"status"}` op stays, fed by the same boards. |
| Credentials: env, then fnox (`fnox.rs`), then the keyring (`login.rs`), TRAIL-545 | Same code, moved to a `factory` module | See below. |
| Docker compute and its gateway container (`trailhead-compute-docker`) | Built in with a `docker` sub-feature | The gateway is a container the compute manages, not part of the server's request path. |
| `ops.rs` (`status`, `logs`), `allow`/`disallow`/`allowed`, `login`, `check` | CLI subcommands (`trailhead factory ...`) | They talk to the server API where a server is needed; `login` and `allow*` stay file/keyring operations. |

### Credentials

The factory resolves Sprites, GitHub, GitHub-writer and Claude tokens from the environment, then fnox (run in the working directory, so it finds the repo's `fnox.toml`), then the keyring. That order stays, with one change forced by the move: the server is usually started in the background by some CLI call, in whatever directory and environment that call had, so the environment and the working directory are accidents. **Proposal:** resolve at control-plane start, not at server start; look in fnox with the directory of each repo in the `repos` list (not the process's cwd), and treat the keyring and `trailhead factory login` as the supported unattended path. The server logs which source each secret came from (never the value), and `trailhead factory check` prints the same. The iroh key and daemon master key stay in the credential store under `factory-keys`, so sandboxes started by the old process are still reachable after the switch.

### Crates and the `factory` feature

The server gains, behind a `factory` feature, these dependencies: `trailhead-factory`, `trailhead-control`, `trailhead-wire` (for `ApiTunnel`, `UiProtocol`, `RemoteDaemon`; TRAIL-1063 moved them out of `trailhead-daemon`), `trailhead-plugins` (the harness and provider lists, TRAIL-1064), `trailhead-compute-sprites`, `trailhead-harness-claude-code` and `trailhead-provider-anthropic` (through `trailhead-plugins`), `trailhead-codehost-github`, `iroh`, and, under `factory-docker`, `trailhead-compute-docker` (and so `bollard`). The code from `trailhead-factory-host` becomes a new crate, `trailhead-factory-server`, which `trailhead-server` depends on only through its `factory` feature (decided). The boundary is one call, "start the factory with this store and this endpoint", so the server knows nothing else about the factory, and the server's own tests and a build without the feature never compile Sprites, Docker or GitHub code. Since TRAIL-1064 the harness and provider lists are in `trailhead-plugins`, so the new crate needs neither `trailhead-daemon` nor its own copy of them.

Rules that keep the engine lean:

- `trailhead-server` and `trailhead` each have `factory` (default on, decided) and `docker`. A build with the feature but no repos configured runs no factory code ([Lifecycle](#lifecycle)). With `--no-default-features` the server has no factory crates, and `trailhead factory ...` prints "built without the factory feature". A CI job builds `-p trailhead --no-default-features` and checks `cargo tree` has no factory crates. It doesn't check for `iroh`: iroh is meant to become how anyone reaches a server remotely, factory or not ([Lookout and remote access](#lookout-and-remote-access)), so it will move into the plain server.
- `trailhead-core` and `trailhead-client` never depend on the factory crates, as now (principle 10). The CLI keeps the `[factory]` tables unparsed in `.trailhead.toml` and `config.toml`; only the server's factory module parses them.
- **Publishing.** The factory crates are `publish = false`, and a published crate can't depend on an unpublished one, even optionally. So `cargo install trailhead` stays the lean engine until the factory crates are publishable; until then the `factory` feature builds from this repo (`cargo install --path crates/trailhead --features factory`). Publishing them (or vendoring the control plane into one crate) is deferred (decided: nothing about the factory is published yet). **Constraint for step 2:** `trailhead-server` and `trailhead` are both published today (`release.yml`), and `cargo package` refuses a crate with any dependency that has no version, optional or not (TRAIL-1066 found this). So the server's `factory` feature, even off by default, can't land until one of these holds: the factory crates publish, the factory build comes from a separate unpublished crate (one that depends on `trailhead-server` rather than the other way round), or `trailhead-server` and `trailhead` stop publishing for a while. *Decided (Lane, 2026-11-07):* nothing is being published for now, so it isn't settled yet: CI's `cargo package` check leaves out `trailhead-server` and `trailhead` (TRAIL-1067), and `cargo publish` of them would fail until one of the three holds. Revisit it before the next publish.
- The daemon stays a separate binary built for Linux x86_64 and uploaded to sandboxes; it is not linked into the server (`daemon_binary::resolve` is unchanged).

## Lifecycle

**Start.** `trailhead serve` (which the CLI spawns) starts the control plane after the HTTP listener is bound and the store is open, and only if the factory is configured: the `factory` feature is on **and** the user config's `[factory] repos` lists at least one repo (decided; there is no separate `enabled` key). Opt-in matters because any `trailhead` command can auto-start the server, and a bare `trailhead ready` must never begin spending money on sandboxes. A server with the feature but no repos listed behaves exactly as today. `trailhead factory disable` turns it off without editing the list by hand (`[factory] disabled = true`, TRAIL-1068; the CLI sets it without a server and says to restart one that's running) and `trailhead factory enable` turns it back on.

Start order: take the control-plane lock, read configs, resolve credentials, find the daemon binary, bind the iroh endpoint, build each repo's `Factory`, then spawn the run loops. What happens when that fails depends on whether a person can fix it in config (decided):

- **Configuration errors stop the server.** A repo whose file won't parse, colliding queues, an unknown harness or provider, a repo directory that doesn't exist: the server exits, and the CLI command that tried to start it prints the error. A server that is configured for the factory but can't run it is broken, and saying so loudly beats a factory that silently isn't running.
- **Outside failures don't.** The Sprites API or GitHub unreachable, the keyring still locked after a reboot, a daemon release that can't be downloaded: the server starts, serves the API, reports `control: starting(reason)` in `/v1/factory/status`, and retries the factory part with backoff. Otherwise a Fly outage would take down the task list.
- **The escape hatch works with no server.** Because a failed start takes every `trailhead` command (and MCP) down with it, `trailhead factory disable` must not need a server: it edits the user config and returns. The error a failed start prints names it.

**Stop and drain.** Today the factory process treats the first Ctrl-C as drain (no new runs, in-flight runs finish) and the second as cancel, and the server stops on SIGINT or SIGTERM after finishing requests (`DRAIN`). Both can't hang on the same signal. **Proposal:**

- SIGTERM or the first SIGINT stops the HTTP listener's *new work* in the factory sense: the control plane drains. The server keeps serving requests while runs finish, because runs and sandboxes call the API through the tunnel and need it.
- A second signal cancels the runs (they requeue on the next start, as now), then the server's own graceful shutdown proceeds.
- `trailhead server stop` sends SIGTERM and waits; with runs in flight that can take an hour. So `stop` prints "draining N run(s); run `trailhead server stop --now` to cancel" and `--now` sends the second signal. A drain has no timeout of its own other than the run budgets. **Guess:** that is right for a manual stop.
- `trailhead server restart`, and the CLI's automatic restart after a reinstall, are the dangerous part. The CLI restarts a server whose binary is newer than the one it runs, on any command, with a SIGTERM. A person running `mise run install` while three runs are live would drain a long time or, if the CLI doesn't wait, get killed mid-run. Decided, in two steps:
  - **First (step 5):** the automatic restart doesn't touch a server with runs in flight. It leaves the old server running and prints "a newer trailhead is installed; N runs are in flight; restart with `trailhead server restart` when they finish". `/v1/health` reports the number of runs in flight so the CLI can tell. The old server keeps working, so nothing breaks.
  - **Then (its own task):** restart once quiet, automatically. When the CLI sees a newer binary and runs in flight, it tells the server an upgrade is waiting. The control plane stops claiming new tasks, and when the last run ends the server restarts onto the new binary. A run can take an hour, so `trailhead server restart --now` stays as the override.

Cancelling is always safe in the sense the code already guarantees: reconcile on the next start puts things right from compute labels and the tracker ([state.md](state.md)). What is in the AGENTS.md rule for `trailhead-control` (record a verdict or spend before teardown) holds unchanged, since the run loop is the same code.

**Waking.** *Built in TRAIL-1070, with two differences:* a watcher per repo rather than one per control plane (each reads only its own project's events, and a server runs a handful of repos), and the 30 s poll stays, because it is also what dirties the loop for reconcile, which notices merged PRs and due reviews; a wake only starts ready tasks. Since TRAIL-1079 the commit signal is the only wake (the timer was for the standalone), and the poll is `TRAILHEAD_FACTORY_POLL_SECS`. `Factory::run_draining` takes a `Notify`. Instead of `wake_on_changes` polling `list_events` every second, the server's module runs one task per control plane on `store.changes()`: on each change it reads the events after its cursor (`list_events` with the three kinds, as `wake.rs` does now) and notifies the loops of the repos whose project matches. This keeps the event cursor, because the commit signal is only a hint that *something* committed (it says nothing of what), and the table stays the source of truth. The result is no 1-second timer and no fixed latency, the wake follows the commit, and the periodic `--poll` stays as a safety net (default raised from 30 s, **Guess**: 5 minutes). Writes from another process (a second server on the same file is not supported; the CLI always goes through the server) never reach the signal, which is why the poll stays.

**One instance (TRAIL-113).** *Built in TRAIL-1079:* `control.lock` is deleted with the standalone control plane, and the server holds a lock on its data directory instead (`<data dir>/server.lock`, taken in `serve_local` before the store opens): the bind only stops a second server on the same port, and `server.pid` is written, not checked. So a second server on the same data directory, on any port, is refused, and with it a second control plane on the same database, iroh key and sandboxes. `trailhead factory check`, which binds the same iroh identity, takes the same lock. A restart onto a new binary hands it on through the exec (the descriptor is close-on-exec).

## Config

- **Per repo (TRAIL-163):** unchanged. Each repo's `[factory]` table in its checked-in `.trailhead.toml`.
- **Per machine:** the user `config.toml`'s `[factory]` table (`max_sandboxes`, `pause_at`, `repos`), unchanged (TRAIL-167, TRAIL-516). It is where the server finds out which repos to run, so `repos` (a list of directories) is now what turns the control plane on. The server no longer has a working directory that means anything, so the "nearest `.trailhead.toml` above the cwd" fallback goes away for the server; `check` and `--repo` keep it for a person at a terminal.
- **One control plane per repo, in one server.** Each listed repo gets its own `Factory` and run loop sharing the store, the endpoint, the compute targets and the `Host` (the cross-repo sandbox cap), as `setup()` does today. The collision and compute/daemon-agreement checks (`repos::validate`) run at start and fail the control plane, not the server.
- **Reloading.** The merge mode is re-read from the repo file each pass (as now). Anything else needs a server restart (decided). `trailhead factory restart`, which would drain the control plane and start it again inside the running server, isn't built for now.
- **Flags that go away.** `--server` (the process knows its own address), `--poll-secs` (config), `--model-endpoint`, `--sprites-token`, `--github-token`, `--claude-oauth-token`, `--daemon` become either `[factory]` keys in the user config or stay environment variables, since a background server has no flags. **Guess:** `[factory] daemon = "<path>"` for the daemon binary, and the others as they are (env, fnox, keyring).
- **What replaces `trailhead factory run`.** `trailhead server start` (and any command that auto-starts it). `trailhead factory run` becomes "run the server in the foreground", i.e. `trailhead serve` with the factory's log on the terminal, so a person who wants to watch logs and Ctrl-C still can, and `mise run factory` keeps meaning that. `status`, `logs`, `allow`, `disallow`, `allowed`, `login` and `check` keep their names under `trailhead factory`. *Built in TRAIL-1079:* as written, plus it refuses when a server is already running or no repos are listed. `--daemon` and `--poll-secs` are read from `TRAILHEAD_DAEMON` and `TRAILHEAD_FACTORY_POLL_SECS` by the server; the other flags were already env, fnox or keyring.
- **`mise run install`** installs one binary with the features it wants (`cargo install --locked --path crates/trailhead --features factory,docker`) plus the daemon, drops the `trailhead-factory-host` install, and no longer warns about a stale factory process, since the server's restart rules above cover it.
- **Logs.** Two files, as now (decided): the server keeps `server.log` and the control plane keeps `factory.log` (rotating, `logfile.rs`). They are different streams that get read in different ways, so one process writes both, routing the control plane's events (its crates' targets and the `repo` span) to `factory.log`. `trailhead factory logs` keeps reading the factory's.

## Lookout and remote access

- **One endpoint for everything.** The server binds one iroh endpoint when the factory is on and serves `trailhead/api/0` (daemons only) and `trailhead/ui/0` (Lookout: status and the forwarded API); the person-facing API stream joins it with TRAIL-71, below. Lookout dials that one id for the board *and* the map. Its `Api` and `Connection` code doesn't change; what changes is who answers.
- **Daemons and Lookout stay separate protocols** ([ui.md](ui.md#transport)): a compromised sandbox still can't reach `trailhead/ui/0` or factory steering, so the allowlist and the "only daemons this control plane started" check carry over as they are.
- **"Factory stopped".** The map's `Stopped` state and the board's fallback to `NetConfig.server_url` exist because the factory process could die while the server lived (or the reverse). With one process, the stream is either up or the whole server is (then nothing answers and Lookout shows "unreachable" as it already does for a dead control plane). What survives is a control plane that is *not running inside a live server*: no repos configured, `trailhead factory disable`, or still retrying after an outside failure (a configuration error stops the whole server instead). The status op then answers with `control: disabled` or `starting(reason)` instead of closing, and Lookout shows that reason over the board. The loopback fallback goes: it was only ever useful on the machine itself. A UI built without the factory feature on the other end gets an unknown-op reset, the same as a control plane without a status feed today.
- **The `{"op":"status"}` frame** gains a `control` field at the top for that. This is a protocol addition (backward compatible, Lookout ignores what it doesn't know). **Guess:** no version bump needed for an added field.
- **TRAIL-71 (remote access).** Decided direction (2026-11-07): iroh is how anyone reaches a server from another machine, and Lane wants it to be the only way. That makes the endpoint part of the server, not the factory: it moves out from behind the `factory` feature, and the factory adds its protocols (`trailhead/api/0` for daemons, `trailhead/ui/0`) to the server's one endpoint. People and agents get their own API stream on it, gated by the allowlist plus bearer tokens, with something like `trailhead login --endpoint <id>` to dial it. It isn't part of this migration: TRAIL-71 explores it soon, and it needs these earlier choices revisited first:
  - PLAN principle 5 and "Remote access" name tunnels in general (`dumbpipe`, Tailscale, SSH) to a loopback port.
  - The CLI's local-server rules: `is_local` on loopback URLs, the instance id check and `<data dir>/tunnels` (PLAN's Local server lifecycle) all assume a tunnel shows up as a loopback port.
  - `trailhead-wire` depends on `trailhead-factory` for its error and message types; serving remote access from a build without the factory means splitting those off.

## Migration in steps

Each step ships alone and leaves `trailhead-factory run` working until step 6.

1. **Arc the store and move the code (no behaviour change).** `AppState.store` becomes `Arc<Store>`; `trailhead-factory-host`'s `setup`, `fnox`, `login`, `repos`, `surface`, `logfile` move into the new `trailhead-factory-server` crate, and the standalone binary calls into it, so there is one copy. Nothing in `trailhead-server` refers to the new crate yet. Breaks: only the build. Rollback: revert; nothing runs differently. *Task: "Move the factory host's setup into a library".*
2. **Run it in the server, opt-in.** *Built in TRAIL-1067:* the `factory` feature (off by default until step 5) on `trailhead-server` and `trailhead`, `trailhead_factory_server::start`, the two logs, the CLI printing why a server refused to start, and the server creating the `factory` agent itself (listing repos is the consent; `trailhead --as-me agent add` would need the server that isn't up yet). *Built in TRAIL-1068:* `trailhead factory disable`/`enable`, which the start error names. *Built in TRAIL-1069:* the first SIGTERM or SIGINT drains while the API keeps serving, a second cancels; `/v1/health` reports `runs_in_flight` and `draining`; `trailhead server stop` says how many runs it is draining, `--now` cancels them, and `restart` refuses while runs are in flight unless `--now` (the CLI's automatic restart after a reinstall still cancels them until TRAIL-1074). Left for later: `control: starting` is a `factory.log` line until status comes from the server (TRAIL-1071); `trailhead factory run` as a foreground `serve` comes with the built-in `trailhead factory` (TRAIL-1073). `serve_local` starts the control plane when the feature is on and `[factory] repos` is set: configuration errors stop the server, outside failures retry, and `trailhead factory disable` works without a server; `trailhead factory run` becomes a foreground `serve`; the lock and the standalone binary stay. Breaks: a person with `repos` listed and the old binary also running gets the lock error (clear message); a configuration error now stops the server, with the error and `trailhead factory disable` printed by the command that started it. Rollback: remove `repos` (or the feature) and run `trailhead-factory run` as before; reconcile adopts whatever sandboxes the other left. *Tasks: "Start the control plane from the server", "`trailhead factory disable` and `enable`", "Drain and cancel the control plane on SIGTERM/SIGINT, `server stop --now`".*
3. **Wake from the commit signal.** Replace `wake.rs` with the `changes()` watcher; raise the poll default. Breaks: a missed wake (covered by the poll). Rollback: revert to the interval watcher. *Task (TRAIL-158): "Wake the run loops from the store's commit signal".*
4. **One endpoint, one status surface.** *Built in TRAIL-1071, and the loopback port and `status.json` removed in TRAIL-1079;* `status`/`logs` ask only the server. The server serves the status routes to the user's token only (agent tokens, a sandbox's included, get 403, since the stream names every run's commands and paths), the `control` field is `FactoryState`, and `trailhead/ui/0` already came from the server's process since step 2. Lookout's side is TRAIL-1072. The server already binds the iroh endpoint for daemons (step 2); this step moves the status surface onto the server: the status routes into the server's API, `trailhead/ui/0` served by the server's endpoint, and the loopback fallback removed. Drop `status.json` and the loopback port; add `control` to the status frame; Lookout drops the loopback fallback and shows `disabled`/`starting`. Breaks: older Lookout against a newer server (it falls back to showing "factory stopped" until updated), and `trailhead-factory status` from the old binary (no port). Rollback: re-run the old binary; Lookout reconnects to its endpoint id, which is the same key, since the keys stay in the credential store. *Tasks: "Serve factory status from the server API", "Lookout: show control-plane state from the status frame, remove the loopback fallback", "`trailhead factory status`/`logs` over the API".*
5. **The CLI feature, install and the restart rule.** *Built in TRAIL-1073:* `factory` is a default feature of `trailhead` and `trailhead-server` (`docker` stays opt-in, as before); `trailhead factory <cmd>` is built in from `trailhead_factory_server::Command`, which the standalone binary uses too; `mise run install` installs `trailhead --features docker` and the daemon; CI builds `--no-default-features` and checks `cargo tree` for factory crates. `trailhead factory run` became a foreground `serve` in TRAIL-1079 (it first stayed an in-process control plane, which kept the lock, the port and the timer wake alive). *Built in TRAIL-1074:* the CLI's automatic restart after a reinstall leaves a server with factory runs in flight alone (from `runs_in_flight` in `/v1/health`) and says to restart it when they finish. *Built in TRAIL-1075:* instead of only saying so, the CLI sends the server SIGUSR1; the server drains the control plane (no new runs, the API keeps serving), and when the last run ends it execs the newly installed binary in place, keeping its pid and scope. `/v1/health` reports `upgrade_pending`, `trailhead server status` shows it, `trailhead server stop` during the drain makes it stop instead of restarting once the runs finish, and `--now` (`stop` or `restart`) cancels them. The CLI sends SIGUSR1 only to a server that reports `upgrade_pending`, since an older one doesn't handle it and would die of it; an older one just gets TRAIL-1074's note. `factory` (default on) and `docker` features on the `trailhead` crate, once the publishing constraint under [Crates](#crates-and-the-factory-feature) is settled; `trailhead factory <cmd>` built in instead of exec'ing a second binary (TRAIL-116 added the exec); `mise run install` installs one binary plus the daemon; the CLI's automatic restart declines to kill a server with runs in flight; CI builds the variant without the factory. Restarting automatically once runs finish follows as its own task. The person-facing endpoint stream is TRAIL-71's, not this step's. Breaks: scripts that call `trailhead-factory`; a person who relied on the auto-restart killing a stale server. Rollback: `cargo install` the previous tag; the user config is unchanged. *Tasks: "Add the `factory` feature to the CLI and server", "`mise run install` for one binary", "Don't restart a server with runs in flight", "Restart onto a new binary once runs finish", "CI: a build without the factory has no factory crates".*
6. **Delete the standalone binary.** *Built in TRAIL-1076 and TRAIL-1079:* `trailhead-factory-host` is gone, its live Docker test moved to `trailhead-factory-server` (driving `trailhead factory run`, the server in the foreground), and `mise run factory` runs `trailhead factory run`. TRAIL-1079 removed what the standalone control plane needed: `control.lock`, the loopback status port and `status.json`, the timer wake, and the control plane's server check (`ServerCheck`), since it can't outlive the server it runs in. `check`, `status` and `logs` still open the database themselves; TRAIL-1080 moves them onto the server's API. Remove `trailhead-factory-host` and its lock role, update `AGENTS.md`, `operating.md`, `seams.md`, `PLAN.md` (the TRAIL-164 mentions), `overview.md` and `mvp.md`. Rollback: the previous release's binary still works against the same data, because nothing in the store's schema or the keys changed.

No database migration is needed in any step. The files the factory keeps (`factory-keys`, `ui-allowed`, `spend-*.json`, the Docker gateway's directory under `<data dir>/factory`) stay where they are, so every step can go back.

## What can go wrong

- **The server now spends money.** A bug or a bad config in the control plane runs in the same process that serves the API. Mitigation: opt-in; a bad config stops the server with a clear error and an escape hatch rather than half-running; the control plane's run loops are tasks that can fail without the server (as `run_repo` already does per repo) and panics are caught per loop. **Guess:** don't also catch a panic in the iroh accept loop; let the server stay up and report `starting(reason)` while the factory part restarts.
- **Memory and compile time.** `iroh`, `bollard` and the harness code join the server build; a full build is slower. Hence the feature, the separate crate and the CI check of the build without it.
- **A broken factory config takes the task list down.** Decided on purpose (configuration errors stop the server), so `trailhead factory disable` must keep working with no server, and the start error must name it.
- **Restart hazards.** Covered above: the CLI's auto-restart and `server stop` must respect running work. This is the one place a person could lose a run, and even then reconcile requeues it.
- **Secrets in a background process.** Environment tokens set in a terminal aren't there when a CLI call elsewhere starts the server; the keyring and fnox lookups are the supported path and `check` shows what resolved.
- **Two `Store`s no more, but one writer.** The control plane's tracker writes through the server's single writer connection, so a long run-loop write (a burst of metadata updates) queues with API writes. It was true before through SQLite's own lock; now it's in-process and visible in the same tracing. **Guess:** not a problem at one machine's scale.

## Decisions

Lane's answers (2026-11-07) to the proposal's open questions. The sections above carry them out.

1. **Opt-in key:** listing repos in `[factory] repos` turns the factory on; `trailhead factory disable`/`enable` turn it off and on without editing the list.
2. **Failing to start:** configuration errors stop the server; outside failures (network, keyring) start the server and retry the factory part. `trailhead factory disable` works without a server as the escape hatch. A person who wants only the task list can also use a build without the factory.
3. **Reinstalling with runs in flight:** first, leave the server alone and say so; then, as its own task, stop taking new tasks and restart onto the new binary once runs finish, with `trailhead server restart --now` as the override.
4. **Publishing:** deferred; nothing is being published for now (Lane, 2026-11-07). The `factory` feature landed without settling it, and CI's package check leaves out `trailhead-server` and `trailhead` until it is revisited before the next publish (see [Crates](#crates-and-the-factory-feature)).
5. **Remote access (TRAIL-71):** iroh is meant to be the way, and the only way, to reach a server from another machine, so the endpoint becomes the server's, not the factory's. Explored under TRAIL-71 soon; not part of this migration.
6. **Module or crate:** a crate, `trailhead-factory-server`, for a strong boundary.
7. **Logs:** two files, `server.log` and `factory.log`.
8. **Config reload:** restart the server; no `trailhead factory restart` for now.
