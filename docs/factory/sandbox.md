# Sandboxes: Sprites, connectors, environment and egress

> **Design note.** It records decisions and intent; where it says something is built or not, check the code if it matters.

The first `Compute` implementation is Fly.io Sprites. A sandbox holds no raw credentials, reaches only declared egress, refreshes its own environment on demand, and may install dependencies, with the gate at merge rather than at install.

Checked against the Sprites docs on 2026-10-25: [Connectors](https://docs.sprites.dev/concepts/connectors/), [connector catalog](https://fly.io/sprites/ecosystem/), [networking](https://docs.sprites.dev/concepts/networking/), [policy API](https://sprites.dev/api/sprites/policies).

## Credentials through Sprites Connectors

Decided: model access and GitHub go through connectors. The gateway injects the stored credential and forwards the call; the sandbox never sees the token.

- **Model access.** The first-class Anthropic connector (bring your own key) forwards only the Messages API (including token counting and Message Batches) and `/v1/models`; files, skills and admin paths are rejected. The agent targets the connector's gateway base URL. OpenAI, OpenRouter, Fireworks and others have their own connectors, so the provider stays swappable.
- **GitHub.** The connector proxies GitHub's REST API with the authorizing user's permissions and granted scopes. Each sandbox works on its own branch and opens its own PR; it never pushes to a branch another sandbox is working on.
- **Getting code in and out.** The gateway forwards REST paths only, so there's no `git clone` or `git push`. Agents just commit locally; the daemon publishes through the Git Data API (blobs, tree, commit, ref), then opens the PR. The commit is parented on the commit the checkout was at when the run started, not on the base branch's current head: commits carry whole files, so laying them on a newer head silently undid whatever had landed since (TRAIL-161, PR #7). An existing branch must still be at that commit, or publishing fails and the task parks instead of overwriting it. Tested 2026-10-26 (M0): this works end to end at 0.4–1.3 s per call. The commit's author is the OAuth user unless set explicitly, and it's unsigned. Getting the code in: `tarball/{ref}` through the gateway returns a 302 with the Location stripped, and `codeload.github.com` isn't on the allowlist, so tarballs don't work. Decided: the Sprite downloads the repo in one step during bootstrap. For a public repo, bootstrap egress adds `github.com` and `codeload.github.com` and the Sprite runs a plain `git clone`. No credential is needed; Trailhead took 0.4 s for a full clone and 0.3 s for a tarball. The allowlist closes again before agent work. For a private repo, the plan is a `custom_api` connector to `https://github.com` with a fine-grained, single-repo token, so `git clone` (and possibly `git push`) runs through the gateway; untested and deferred (TRAIL-96), since the MVP uses public repos. A last resort that works today is a recursive `git/trees` call plus one `git/blobs` call per file (3.5 s for Trailhead), but that's one API call per file against GitHub's 5,000/hour limit.
- **Access policy.** Default-deny, granted by sandbox label or name prefix. Endpoint allow and block lists exist (API only for now), with exact paths or trailing-`*` prefixes. Policy belongs to the connector, not the sandbox, so author and reviewer roles get separate GitHub connectors with different scopes.
- **Kill switch.** Removing a sandbox's label cuts its model and GitHub access at the gateway. Labels aren't in the OpenAPI spec, but Fly's Go and Python SDKs send them: `labels: [..]` on create, `PUT /v1/sprites/{name}` with `labels` to replace them and `clear_labels: true` to empty them. They're plain strings, so `trailhead-compute-sprites` stores `key=value` pairs and connector policies match on those exact strings (`sprite_labels: ["role=worker"]`). Confirmed against the live API: values such as `repo=lanesawyer/trailhead` are accepted, and `PUT` replaces the set. Still to check: that a label change takes effect at the gateway, which needs a connector restricted by label (TRAIL-95).
- **Managed by API.** Connectors are fully API-managed (`/v1/oauth/connections`: provision, API-key and custom-API connections, access policy, per-connection usage and balance), so the control plane can own their setup. fly-mcp has no connector tools.
- **Media types.** The gateway doesn't pass GitHub's `Accept` media types through: asking for a PR as `application/vnd.github.diff` returns its JSON. So the code host builds diffs from `GET /pulls/{n}/files`.
- **Scopes in practice.** The dashboard's GitHub OAuth connector gets classic `repo,read:org` (every repo the user can reach) and `allow_all` access. Before real use, narrow it with `allowed_endpoints` (`/repos/<owner>/<repo>/*`) and a label or name prefix, or use a fine-grained token or GitHub App through a `custom_api` connector.
- **Discovery.** Inside a sandbox, `GET https://api.sprites.dev/v1/gateway/list` (no auth header; the gateway identifies the Sprite) returns each ready connector's `gateway_base_url` (`https://api.sprites.dev/v1/gateway/<provider>/<connection_id>`). The only egress domain the gateway needs is `api.sprites.dev`. Every Sprite ships a `sprite-api-gateway` skill for Claude Code, Codex, Cursor and Gemini.
- **The one credential a sandbox holds** is its short-lived, project-scoped Trailhead sub-agent token; see [state.md](state.md).

**Subscription mode** (TRAIL-101, opt-in, for the maintainer's own use): `trailhead-factory run --claude-oauth-token …` (or `CLAUDE_CODE_OAUTH_TOKEN`, from `claude setup-token`) runs Claude Code in sandboxes on a Claude subscription instead of a model connector. The token travels in the daemon's `0600` secrets file (kept, so a cold wake can restart the daemon), never in run requests or on a command line. Claude Code gets it as `CLAUDE_CODE_OAUTH_TOKEN`, with any API key or base URL stripped, and agent egress adds `api.anthropic.com`. The trade-offs: it breaks "sandboxes hold no raw credentials", since an injected agent could leak a token good for the whole subscription; spend is priced at API rates as a proxy, since a subscription has rate limits rather than per-call prices; parallel sandboxes share the plan's limits; and whether the plan's terms allow unattended use is for the maintainer to confirm. The connector stays the design beyond the maintainer's own use.

Assumed to work, not yet tested (TRAIL-97): Claude Code's exact setup (likely `ANTHROPIC_BASE_URL` set to the gateway URL plus a placeholder key), and whether the gateway's 120-second timeout, documented for several connectors, cuts off long streaming calls. The connector takes an API key; a Claude subscription doesn't plug into it.

## Standard checks

Decided: repos describe their stack and a fixed set of named checks. mise is an implementation detail the user never touches.

```toml
[factory.stack]
tools = { rust = "stable", node = "lts" }

[factory.checks]
fmt       = "cargo fmt --check"
fmt_fix   = "cargo fmt"
lint      = "cargo clippy -- -D warnings"
typecheck = "cargo check"
test      = "cargo nextest run"
build     = "cargo build"
```

- **Fixed names, optional entries.** `setup`, `trim`, `fmt`, `fmt_fix`, `lint`, `typecheck`, `test`, `build`. A repo leaves out what it doesn't have.
- **Contract.** Exit code 0 is a pass. Structured output (JUnit, SARIF) can come later.
- **Generated, not hand-written.** The factory turns `[factory.stack]` and `[factory.checks]` into mise tools and tasks when it bootstraps a sandbox. A repo with its own `mise.toml` keeps it, with the factory's tasks merged in.
- **Policy refers to names.** Gates say which checks must pass (`require = ["fmt", "lint", "test"]`), so policy reads the same across stacks.
- **Onboarding.** An agent can inspect a new repo and propose `[factory.stack]` and `[factory.checks]` for a human to confirm.

This lives in the per-repo factory file, with agent profiles ([agents.md](agents.md)) and gate policy ([review.md](review.md)).

## Bootstrap and checkpoints

Decided 2026-10-27, replacing a fresh Sprite per task (decided 2026-10-26): workers run in a lazy per-repo pool of warm Sprites, each restored to its own checkpoint before every task. A cold build of Trailhead took about 6½ minutes in the first real run (TRAIL-103), too long to pay on every task.

- **Why not seed from a shared checkpoint.** Tested in M0: a checkpoint can't seed a different Sprite. Checkpoint IDs are a per-Sprite sequence (`v1`, `v2`, …). Restoring a Sprite to its own checkpoint works and takes about 1.5 s.
- **Lazy pool.** Worker Sprites are `<repo>-w<n>`, labelled `pool=worker` and `state=idle|busy`, plus `warm=<checkpoint>`. A task takes an idle one, or creates one when none is idle; the tick's room check keeps the pool within `max_sandboxes`. A new one pays the cold build once.
- **Per task.** Mark busy (with `task` and `role` labels), open install egress, restore the warm checkpoint, prepare (fetch and reset onto the base branch, then the `setup` check, an incremental build), checkpoint the result as the new warm point, narrow egress, run.
- **Isolation.** When the task ends, the Sprite is restored to its warm checkpoint, which wipes everything the task wrote, then marked idle with no `role` label (so no connector access) and no egress. Idle Sprites pause and cost only storage. Parked tasks keep their Sprite busy.
- **Reconcile.** Pooled Sprites are never destroyed at boot; one an interrupted run left busy goes back to idle.
- **Broken Sprites.** A pooled Sprite that keeps failing to release (TRAIL-135: Sprites answered `503 Storage not ready` for 25 minutes) is retried with backoff from 30 s up to 5 min. After five failures or ten minutes, the factory gives up on it. It destroys the Sprite if the API allows, and otherwise labels it `state=broken` with no `role`, then destroys it on a later reconcile once the API recovers. A broken Sprite doesn't count toward `max_sandboxes`, so the next task gets a new one. If even the labels can't be changed, the control plane leaves it out in memory until it restarts. The failure counts are in memory too.
- **Reviewers** get a fresh Sprite each and skip `setup`, since they only read the diff.
- **Bootstrap.** The stock image (Ubuntu 26.04, glibc 2.43) ships rustup/cargo, node, python, go, `gh`, git and Claude Code, but not mise. Uploading and starting the daemon and cloning takes about 11 s.
- **Later:** deleting Sprites idle for N days, and a shared build cache in object storage for big pools, behind the same `Compute` seam.

## Egress policy

Sprites egress is a DNS-based allowlist set from outside through the API. Changes are enforced about a second after the API call returns: in the M3 live test, a `git fetch` sent right after narrowing still reached GitHub. So each run request lists the hosts the narrowing dropped, and the daemon waits until they stop resolving before the agent starts. It's read-only inside the sandbox, and changes apply live and flush existing connections. An empty rule list means unrestricted, so deny-by-default is an explicit `{"domain": "*", "action": "deny"}` plus allows. Denied names return REFUSED. A raw IP is reachable only after a lookup of an allowed domain resolved to it, and private IPs are always blocked. The `{"address", "protocol", "port"}` rules in fly-mcp's schema are rejected by the Sprite ("invalid policy config") and absent from the OpenAPI spec, so don't rely on them. `{"include": "defaults"}` is a broad development preset (GitHub, npm, PyPI, Docker Hub, AI APIs) and too wide for agent work.

| Phase | Allowed domains |
| --- | --- |
| Install | Iroh relay and discovery, connector gateway, the repo's package registries and mise tool sources; `github.com` and `codeload.github.com` at bootstrap for public repos |
| Agent work | Iroh relay and discovery, connector gateway |
| Install requested mid-task | Install set, opened by the control plane on the daemon's request and closed after; each request logged |

Decided: registry egress only during install phases. The risk isn't secrets, since the sandbox holds none; it's a malicious or typosquatted package whose install script acts with the sandbox's connector identity. Mitigations:

- **New dependency raises the grade.** Adding or upgrading a dependency is at least grade 3 by default, configurable per repo ([review.md](review.md#grades)).
- **Supply-chain checks.** An audit tool per ecosystem (for example `cargo-deny` or `osv-scanner`) runs with the other checks.
- **Narrow connector scopes.** An author sandbox's GitHub connector reaches only its own repo.

## Keeping warm images small

Decided 2026-10-31 (TRAIL-581). Every task exports and imports the sandbox's warm checkpoint, so its size is paid per task, and a pool per repo multiplies it. The daemon knows no stack; the repo says what to cut.

- **`trim`.** An optional check beside `setup` in `[factory.checks]`. A worker's prepare runs it after `setup` and before the warm checkpoint, from the checkout root. A failure is logged and the sandbox goes on untrimmed. `$TRAILHEAD_DAEMON` is the path of the daemon binary in the sandbox.
- **Cargo.** `trailhead-daemon trim-cargo --cap <bytes> [--target <dir>]` is the cargo logic (below). Trailhead's own `.trailhead.toml` has `trim = "\"$TRAILHEAD_DAEMON\" trim-cargo --cap 6442450944"`. It replaced `[factory.daemon] target_cap_bytes`, which now fails to parse.
- **A stack-neutral limit.** After `trim`, the daemon reads the use of the filesystem holding the checkout (`df`). Over `[factory.daemon] disk_warn_bytes` (default 16 GiB; 0 for none) it logs a warning. Over `disk_limit_bytes` (default 0, no limit) the prepare fails, so no warm checkpoint is taken and the sandbox is destroyed, and the task fails with the number in its error. Use the limit once a stack's sizes are known. The measure is the whole filesystem, not just the checkout, so it includes the toolchain and base image.
- **Suggestions per stack**, to set `trim` to; none is measured here, so check against your repo and a warm rebuild time before relying on one:
  - Node: `rm -rf .next/cache node_modules/.cache` (framework caches regrow on the next build); keep `node_modules` itself, since `setup` runs with egress and the agent's phase doesn't. A package manager's download cache (`npm cache clean --force`, `pnpm store prune`, `yarn cache clean`) can go.
  - Python: `uv cache prune --ci` (or `rm -rf ~/.cache/pip`); keep `.venv`. Remove `.pytest_cache`, `.mypy_cache`, `.ruff_cache`.
  - JVM: `rm -rf .gradle/caches/*/transforms build/tmp` and delete `~/.gradle/caches/build-cache-*`; keep downloaded dependencies (`modules-2`) the agent's phase can't fetch again. For Maven, `rm -rf target` of modules `setup` doesn't need to rebuild.
  - Go: `go clean -cache` drops the build cache (a rebuild is slower); the module cache stays.
  - Anything else: `du -sh` the checkout and `$HOME` after `setup` in a sandbox, delete the regenerable part, and set `disk_warn_bytes` just above the result.

## Docker

Decided 2026-10-28 (TRAIL-119): `trailhead-compute-docker` runs sandboxes as containers on a Docker engine (or Podman's Docker API), for agents on your own machine. `.trailhead.toml` picks it with `[factory.compute] kind = "docker"`, optionally with `image`, `network` and `runtime` (an OCI runtime such as `runsc`). The `trailhead-factory` binary needs the `docker` feature for it.

- **The engine on a dev machine.** `mise run docker-up` starts rootless Docker in a lima VM with no host mounts, so nothing is installed system-wide and a container escape lands in the VM, not beside the control plane and the Trailhead database. mise installs lima and the Docker CLI; on Linux, qemu and access to `/dev/kvm` are the one prerequisite it can't install (on macOS lima uses the built-in Virtualization framework). `docker_host` in `mise.toml` is the VM's socket, and the Docker tasks set `DOCKER_HOST` to it. colima was tried first and dropped: it forces lima's `user-v2` network on Linux, and qemu 10.2 aborted in that path (`net_fill_rstate: Assertion 'size == 0'`) as soon as an image build pulled packages. lima's own `docker` template uses slirp and doesn't hit it.
- **Identity and labels.** A sandbox's id is its container name, which survives a restore. Docker labels can't change after creation, so labels and egress live in one JSON state file per sandbox under `<data dir>/factory/docker`; the container carries only `dev.trailhead.sandbox=<name>`, which `list` filters on (`docker ps --filter label=dev.trailhead.sandbox`).
- **Checkpoints.** The paused container's filesystem exported and imported as a one-layer image `trailhead-checkpoint:<name>-<millis>`, labelled `dev.trailhead.checkpoint-of=<name>` and `dev.trailhead.checkpoint-note=<note>`, with the container's user, working directory and environment carried over. Not a `docker commit`, which stacks a layer on the last image: a pooled worker checkpoints after every task, and the chain kept every rewritten `target` (14 tags came to 48 GB in a live run and filled the disk, TRAIL-176). Restoring removes the container and recreates it from that image with the same name, labels and egress. Each warm checkpoint removes the sandbox's earlier warm ones that no label points at; a parked sandbox's checkpoint is kept, and all go when the sandbox is destroyed. A sandbox's disk use is its container plus about one image, so a pool of N workers needs about N times the repo's built size twice over. Before a run starts the control plane calls `Compute::preflight`, which for Docker fails when the engine's disk has less than `min_free_bytes` (10 GiB) free. Unlike a Sprite checkpoint, an image could seed other containers (TRAIL-93).
- **Capping `target` (TRAIL-553, moved behind `trim` by TRAIL-581).** Left alone, a worker's `target` is the repo's whole build and a warm image is about that size, so every task exports and imports it. This repo's `trim` check (see "Keeping warm images small" below) is `"$TRAILHEAD_DAEMON" trim-cargo --cap 6442450944`, which trims `target` to 6 GiB with the logic below. First every `incremental` directory goes: the biggest part and the least reusable across commits. If it is still over, whole compilation units go, least recently used first: a crate's `.fingerprint/<name>-<hash>`, its `deps/<name>-<hash>.*` files and its `build/<name>-<hash>` directory, together or not at all. Never single files, because cargo decides a build script is fresh from its fingerprint and `output` file and doesn't look in `OUT_DIR`, so a lone deleted native library (`aws-lc-sys`) or generated source would break the link instead of triggering a rebuild; without the fingerprint cargo reruns the unit and its build script. A unit's last use is its fingerprint's `invoked.timestamp`, which cargo touches for every unit a build considers, so units setup didn't need (older commits' leftovers) go before the ones it did; files with no fingerprint go first of all. Measured on this repo (`cargo build --all-targets --locked`, one line appended to `trailhead-core/src/lib.rs`, 2026-10-31): a warm rebuild took 14 s with `target` at 8.2 GB. Trimmed to the default 6 GiB (`target` 6.0 GB after the trim), the rebuild took 38 s. Trimmed to 4 GiB it took 131 s, and from a 3 GiB trim 139 s, because the cap then starts evicting the third-party dependencies every build reuses. So the default costs about 24 s per task and saves about a quarter of the disk; going lower costs far more than it saves. The rebuild regrows `incremental`, which the next prepare removes again, so a sandbox's disk is bounded by the cap plus what one task builds, not by how many tasks it has run. Builds after each trim succeeded, and tests in `trim.rs` check that a trimmed unit leaves neither half of itself. Not done: one build cache shared between pooled sandboxes (a bind-mounted `CARGO_TARGET_DIR` would need locking across concurrent builds and lets one task's artifacts leak into another's; it is the next step if per-sandbox caps cost too much build time).
- **Programs.** A small shell supervisor (`supervise.sh`) is uploaded at create and is the container's main process, under Docker's init, with `restart: unless-stopped`. `start` writes the files as the container's user (each beside its target, then renamed over it), writes a run script, and has the supervisor (re)start the program, restarting it whenever it exits. After a restart or restore, the supervisor starts every program again. A program that exits within 3 seconds fails `start` with its output, as on Sprites.
- **Wake** starts a stopped container; containers don't pause.
- **Egress and networks.** Built (TRAIL-419). Each sandbox has its own `--internal` network, `trailhead-sb-<name>`, shared only with the gateway's container, and egress is the gateway's allowlist for it. Sandboxes get `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` and their lowercase forms (curl reads only the lowercase `http_proxy`), and run without `NET_RAW` or `NET_ADMIN`. The `network` setting is now the ordinary bridge network the gateway gets out on (default `trailhead-gateway-out`); sandboxes are never on it. Docker's default address pools hold about 31 networks, which caps sandboxes on one engine at about 30 (TRAIL-499). The gateway's container is labelled with the SHA-256 of the daemon binary it was made with, and a gateway with a different (or no) label is removed and recreated, so a new daemon binary takes effect (TRAIL-500); sandboxes are re-attached by the resync that follows.
- **Credentials.** `DockerCompute` pushes connections to the gateway on an exec's stdin. Today that's GitHub, from `GITHUB_WRITER_TOKEN` or `trailhead factory login github-writer`, and never the read token. With no writer token, the control plane warns and sandboxes can't publish. Model access is subscription mode only: the OAuth token is in the sandbox, and Claude Code reaches `api.anthropic.com` through the proxy, so a run can't yet meet "no key in the sandbox" (TRAIL-487). There's no API key handling.
- **The image.** `mise run docker-image` builds `trailhead-sandbox:latest` from `crates/trailhead-compute-docker/image`: Ubuntu 26.04 with git, a C toolchain, rustup and Claude Code, as the user `trailhead`. The daemon lives in `/home/trailhead/.trailhead` and checks out into `/home/trailhead/work`. It's the same Ubuntu as the stock Sprite, so a daemon built on the maintainer's machine runs in both.
- **Isolation.** Containers share the engine's kernel. On a dev machine that's the lima VM's; on a bare Docker host, prefer gVisor (`runtime = "runsc"`) or rootless Docker (TRAIL-177).
- **Tests.** `mise run test-live-docker` runs the lifecycle and the gateway against the engine, on `trailhead-sandbox:latest`, with a gateway of their own: egress refused off the allowlist and allowed on it, no route or DNS around the proxy, dropped capabilities, narrowing (open tunnels too), one sandbox unable to reach another, the GitHub connection listed only with a `role`, and recovery from a gateway restart, a removed gateway and a new control plane. Their GitHub credential is a dummy that's only listed, never sent upstream. `mise run test-live-docker-credentials` uses real tokens from fnox: one Claude Code call through the proxy, and one read-only GitHub call through the gateway, where the sandbox sends a junk credential and the gateway replaces it. `mise run test-live-docker-factory` (TRAIL-413) runs the whole factory on a small task in a scratch repo (`TRAILHEAD_LIVE_REPO`, public, with real fnox tokens): the worker opens a PR through the gateway, a reviewer reviews it, and during each agent's work the test checks that `example.com` is refused (and logged by the gateway), that neither GitHub token is in the sandbox's environment or git config though the gateway answers GitHub for it, and, for the worker, that removing the `role` label turns its GitHub calls into 403s until the label is back. Subscription mode, so no model-key check until TRAIL-487. It shares the engine's `trailhead-gateway`, so it refuses to start beside another factory. Written in a factory sandbox, which has no Docker engine: it compiles and lints (CI lints it with `--features docker`) but has not been run, so nothing surprising is recorded yet. A person must run it against the lima VM and replace this sentence with what it shows before it is trusted. The label probe changes the labels at the gateway only (not through a second `DockerCompute`, whose resync could delete a sandbox the factory is creating), and cuts the worker's GitHub for a few seconds mid-run, so a push in that window can fail.

### The gateway: credentials and egress for Docker sandboxes

Built (TRAIL-174, TRAIL-175, TRAIL-419), except that the gateway holds no model credential yet (TRAIL-487). Designed 2026-10-29 (TRAIL-404): one small proxy, the **gateway**, does for Docker sandboxes what Fly's connector gateway and DNS allowlist do for Sprites. It covers both TRAIL-175 (credentials) and TRAIL-174 (egress), because they're one problem: a sandbox's only way out is the gateway, and the gateway decides what goes through and adds the keys.

**Where it runs.** In its own container on the same Docker engine, `trailhead-gateway`, started and kept up by `DockerCompute`. Not in the control plane process: on a dev machine the engine is in the lima VM, and a container on an internal network can't reach the host. It's the one container with a route out. It holds the keys in memory only. A sandbox escape lands in the VM beside it, which is no worse than today's subscription mode, where the sandbox holds the token itself.

**Networks.** Each sandbox gets its own `--internal` network, `trailhead-sb-<name>`, with only the sandbox and the gateway on it. An internal network has no route out and no external DNS, so anything that doesn't go through the gateway fails closed. Separate networks also keep sandboxes from reaching each other, and they tell the gateway which sandbox a request came from by the network it arrived on, not by a source IP. Sandboxes run without `NET_RAW` or `NET_ADMIN`. The gateway is also on a normal bridge network to get out. The shared `trailhead-sandboxes` network is gone.

**Egress (TRAIL-174).** The gateway is an HTTP forward proxy (CONNECT for HTTPS, plain forwarding for HTTP). Sandboxes get `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` in their environment, which git, cargo, rustup, mise, npm, curl and Claude Code all honor. Each sandbox has a domain allowlist with the same rules as a Sprite's: exact names and `*.` wildcards, and nothing means nothing. `set_egress` returns once the gateway has the new list, and narrowing closes the sandbox's open tunnels to hosts that are no longer allowed. So the daemon doesn't need the wait-until-it-stops-resolving step that Sprites need. Each refused CONNECT is logged with the sandbox's name. Non-HTTP traffic (git over ssh, raw UDP) has no way out, which is the intent.

Built (TRAIL-174, the gateway core): `trailhead-daemon gateway --listen <addr> --socket <path>` is the proxy and control socket, and `trailhead-daemon gateway-ctl --socket <path>` sends it one JSON message from stdin (`register`, `unregister`, `set_egress`, `state`; types in `trailhead-factory`'s `gateway` module). There's no HTTP dependency: the proxy parses only the request head by hand, rewrites a plain request to origin form with `Connection: close`, and copies bytes after that, so bodies and streamed responses pass through untouched and each plain connection carries one request. A `register` carries the gateway's own address on the sandbox's network, and a request is attributed to the sandbox registered for the local address it arrived on. `*.example.com` matches subdomains only, not `example.com`. `--listen` defaults to port 3128; `DockerCompute` passes port 8080 (`GATEWAY_PORT`).

Built (TRAIL-175, the credentials half): a request in origin form (not a proxy request) is addressed to the gateway itself. `GET /v1/gateway/list` lists the connections the calling sandbox's role may use, with `gateway_base_url` built from the request's `Host`. `/v1/gateway/<provider>/<id>/...` is forwarded to the connection's upstream with the stored credential (`Authorization: Bearer` or `x-api-key`, per the connection's `auth`) added and every credential header the sandbox sent removed. Responses stream as they arrive, with no total timeout and no redirects followed; request bodies need a `Content-Length` (32 MiB at most). Connections are data, set over the control socket (`set_connection`, `remove_connection`: provider, id, upstream, auth, credential), so a model server on the host is one more entry with provider `model`. They live in memory only, `Debug` redacts the credential, and `state` omits it. Policy is by provider and the sandbox's `role` and `repo` labels, as method plus path-prefix rules (`*` matches one segment); a refusal is a 403 with the reason, and `..` or encoded slashes and dots are refused. Worker on GitHub: Git Data (GET, POST, PATCH), pulls and issues under `/repos/<repo>`, with no merge or delete. Reviewer: reads under the repo, plus POST to issue comments, PR comments and PR reviews. Anthropic: `/v1/messages` (with token counting and batches) and `/v1/models`. No role, or an unknown one, gets nothing.

**Iroh.** iroh 1.4 sends relay traffic and pkarr publishing and lookups through an HTTP proxy (`Endpoint::builder().proxy_url`, or `proxy_from_env`). So the daemon reaches the control plane through n0's relays over the gateway, as on Sprites. That revises TRAIL-174's plan, written when we thought iroh couldn't use a proxy, to dial the control plane directly on the local network.

Tested 2026-10-30 (TRAIL-412). A container on an `--internal` network in the lima VM, whose only way out was a small CONNECT proxy, talked to a control plane on the host. It used the `N0` preset unchanged plus `proxy_from_env`.
- **Lookup works as is.** The daemon found the control plane by endpoint id alone. The preset's pkarr resolver goes over HTTPS, so through the proxy. The control plane also dialed a sandbox it had never heard from by id alone, found through the sandbox's pkarr publishing via the proxy, in about 0.3 s. So `DaemonSecrets` doesn't need the control plane's relay URL.
- **The allowlist is two names:** `dns.iroh.link` and `*.relay.n0.iroh.link`. Relay names arrive with a trailing dot (`usw1-1.relay.n0.iroh.link.`), so matching must strip it. iroh also tries DNS-over-HTTPS to `1.1.1.1`, `8.8.8.8` and `9.9.9.9` because the container has no DNS. Refusing those is harmless, but they come back about once a second each, so the gateway should log refusals once per host, or the daemon should set a DNS resolver that doesn't fall back to them.
- **All traffic goes through the relay.** Every connection was relay-only, as expected. It came online in 3 s, connected in 0.3 to 0.65 s, and had about 10 ms median round trips through the US-West relay.
- **It survives the proxy restarting.** With the proxy down for 10 s, the sandbox's relay connection came back on its own, and the control plane then dialed it fresh by id.
- **Watch for:** the VM's Ubuntu ships AppArmor profiles that attach to binaries by path even inside rootless containers. Its `tinyproxy` profile blocked that proxy from reading its filter file and from being stopped. The gateway being our own binary avoids this.

**Credentials (TRAIL-175).** The gateway speaks the part of Fly's gateway API the daemon already uses, so the daemon and harness barely change:
- **Connector list.** `GET /v1/gateway/list` lists the connections this sandbox may use, each with a `gateway_base_url` of `http://trailhead-gateway:<port>/v1/gateway/<provider>/<id>`. The daemon's list URL moves from a constant to `DaemonSecrets` (`gateway_list`), with Fly's URL as the default.
- **Forwarding.** `/v1/gateway/<provider>/<id>/...` forwards to the upstream with the credential added, and strips any credential the sandbox sent. The upstreams are GitHub (`api.github.com`, `Authorization: Bearer`) and Anthropic (`api.anthropic.com`, `x-api-key`). A model server on the host (TRAIL-126, [local-models.md](local-models.md)) is a third.
- **Model endpoint.** With Docker compute, the control plane sets each run's endpoint to the gateway's Anthropic URL instead of `--model-endpoint`. The harness already sends a placeholder key to whatever base URL it's given.
- **Per-role policy.** The kill switch and per-role scopes work as on Sprites. The gateway knows each sandbox's labels, and a sandbox with no `role` gets no connections. Policy per role is a list of allowed method and path prefixes. A worker gets the repo's Git Data, pulls and issue-comments endpoints. A reviewer gets reads plus PR comments and reviews. An idle pooled sandbox gets nothing.
- **Where the keys come from.** The same places the control plane already reads them: the environment, else the credential store that `trailhead factory login` writes (TRAIL-117). GitHub needs a token that can push and open PRs, which is more than the read token `login github` checks for today. The Anthropic API key would be a new login. Subscription mode stays as it is (token in the sandbox) until the gateway can carry the OAuth token too, which is an open question below.

**How the control plane drives it.** `DockerCompute` owns the gateway like any other container. It creates the gateway on first use from the sandbox image, uploads the daemon binary, recreates it if it's gone, and updates it through `docker exec` of `gateway-ctl`, which talks to a control socket inside the container, so nothing new listens on a network. It pushes three kinds of update: sandbox registration (name, the gateway's address on that sandbox's network, labels), egress lists, and credentials (on the exec's stdin, so they're on no command line). The gateway is a `gateway` mode of the `trailhead-daemon` binary, which is already built for Linux and uploaded, so it adds no second artifact.

Built (TRAIL-419). The gateway's memory can vanish behind the control plane's back, since Docker restarts it on its own, so the state files are the truth. `DockerCompute` remembers the start time of the gateway run it last synced, and checks it before each change and every 5 seconds, so a running sandbox isn't left cut off until the next call. Any other start time, including a new control plane's first look, pushes the full state again. That resync also unregisters sandboxes with no state file, removes connections no longer configured, and finishes teardowns that stopped partway (`destroy` removes the state file last, for this reason). One lock covers each state-file change and its push, so a resync can't restore an allowlist that a concurrent `set_egress` just narrowed. The gateway runs as root in its container, to own its socket under `/run` whatever user the image has, with every capability dropped. It isn't replaced when the daemon binary changes (TRAIL-500).

**Considered: everything over iroh.** Sandboxes would get no network except iroh, and the control plane would proxy GitHub, the model API and package registries itself, as the API tunnel already does for Trailhead. The upsides:
- Keys never leave the host.
- One path works for every compute.
- There's no gateway container to run.

Dropped, for the same reason [local-models.md](local-models.md) dropped it for model calls on Sprites: it makes the control plane relay everything.
- **All of it goes through relays.** A sandbox on an internal network can't holepunch, so every byte goes through n0's public relays, which are rate-limited and not meant for bulk traffic. A cold setup alone is hundreds of MB of toolchain, crates and clone.
- **Model calls take a detour.** Every streamed response goes upstream, then the control plane, then a relay, then the sandbox. That adds latency to each agent step and makes the control plane a bottleneck.
- **Installs need a path out anyway.** The control plane would end up as a general proxy, just a farther one.

The principle the design follows instead, the same as on Sprites: sandboxes reach what they need and is trusted directly, and credentials are added at the nearest trusted hop. On Sprites that hop is Fly's gateway; on Docker it's a gateway container next to the sandboxes. Iroh stays the small control channel between the daemon and the control plane. If a remote Docker host ever makes keys in its VM unacceptable, there's a middle way: the gateway holds no keys and asks the control plane over iroh to sign each credentialed request, while bulk egress still goes out directly.

**Open questions.**
- **Subscription mode through the gateway.** Can Claude Code use a placeholder `ANTHROPIC_AUTH_TOKEN` against the gateway, with the gateway putting in the real OAuth bearer and the `oauth` beta header? If so, Docker keeps "sandboxes hold no keys" even on a subscription.
- **Private repos.** The gateway could forward git's smart-HTTP to `github.com/<owner>/<repo>.git` with the token, so `git clone` works for private repos, which Sprites can't do yet (TRAIL-96). Later, not now.
- **Streaming and timeouts.** The gateway forwards streamed responses as they arrive and sets no total timeout, unlike Fly's 120 s (TRAIL-97).
- **Podman and bare-metal hosts.** On a bare-metal host the gateway sits beside the control plane, so TRAIL-177's runtime defaults apply to it as well as to the sandboxes.

**Order of work.**
1. **Spike (done, TRAIL-412):** iroh through the proxy works with the stock preset; see above.
2. **Gateway egress:** the proxy, per-sandbox networks, the control socket and `set_egress` (TRAIL-174).
3. **Gateway credentials:** the list and forwarding API, the role policy, `gateway_list` in `DaemonSecrets`, the endpoint override, and the API-key and write-token logins (TRAIL-175).
4. **A live run:** a Trailhead task end to end on Docker (`mise run test-live-docker-factory`), worker and reviewer.

## Keeping a sandbox awake

A Sprite pauses about 30 seconds after its last inbound activity (an exec, a request to its URL), and pausing drops every open connection. Services don't count as activity, and neither does the daemon's outbound iroh connection: in M4's live test, a run's connection dropped about a minute in. So while a prepare or run is in flight, the daemon holds the Sprite with the Tasks API on `/.sprite/api.sock`: a 5-minute expiry refreshed every minute, so a crashed daemon frees the Sprite on its own. When a request ends, the hold is cut to 90 seconds rather than deleted. A Sprite that's been idle past its window pauses the moment its last hold goes, which froze one between a worker run and its review. A paused Sprite isn't woken by an iroh dial, so the control plane calls `Compute::wake` before redialing a daemon it isn't connected to. On Sprites that's an exec that takes a 2-minute hold; an exec alone isn't enough, because an idle Sprite pauses again as soon as the command ends. The daemon notices the resume (its wall clock jumps), re-resolves iroh's hosts and reconnects. Verified live: a review ran 1.8 s after waking a Sprite that had been paused for a minute.

## Iroh in a locked-down sandbox

Iroh runs in every phase: Trailhead's `dumbpipe` tunnel is the sandbox's only channel to the control plane and Trailhead.

Tested 2026-10-26 (M0) with dumbpipe 0.40.1. The Sprite was NATed at 10.0.0.1; the peer was the maintainer's machine behind home NAT, 46 ms ICMP RTT away.

| Policy | Path | Steady RTT on one connection |
| --- | --- | --- |
| None | Direct UDP | 47 ms |
| Deny `*`; allow `iroh.link`, `*.iroh.link`, `*.iroh-svc.com` | n0 relay (`usw1-1.relay.n0.iroh.link`) | 51.6 ms p50, 52.1 ms p90 |
| As above, plus an allowed DNS name for the peer's IP, resolved once in the Sprite | Relay, then upgraded to direct | 47 ms |

Decided: relay-only is fine for the MVP. On n0's public relay it costs about 5 ms, so a self-hosted relay isn't needed yet. Agent-work egress for iroh is `iroh.link`, `*.iroh.link` and `*.iroh-svc.com` (the relay hosts CNAME there). Connecting, including the first round trip, takes about 270 ms.

Leaning: the optional direct path is a DNS name for the control plane's public IP (its own domain, or sslip-style), added to the Sprite's allowlist and resolved by the daemon before it dials. Without the lookup, the IP stays blocked and the connection stays on the relay. Untested: what happens when that record's TTL expires mid-connection.

Narrowing egress resets which raw IPs a Sprite lets through, and iroh redials relays by IPs it resolved earlier. So after a lockdown, every relay reconnect was refused and the run's connection died about 30 seconds later. That happened in about half of M5's live runs. The daemon now resolves iroh's relay and discovery hosts again through the system resolver after each lockdown, and every minute after that, then tells iroh the network changed.

`dumbpipe connect-tcp` opens a new iroh connection for every TCP connection, which costs about 2 RTT per short request (105–112 ms here). The daemon should hold one long-lived iroh connection and multiplex streams on it.
