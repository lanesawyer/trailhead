# Operating the factory

> Running the factory today. For what it is and how a task flows through it, read the [overview](overview.md) and [lifecycle](lifecycle.md) first.

How to run the factory day to day, as it works today. It assumes this repo and its dev setup; the path to running it without the repo is TRAIL-114.

## One-time setup

- `BWS_ACCESS_TOKEN` in your environment, for a Bitwarden Secrets Manager machine account with read access to the Trailhead project. `fnox.toml` maps `SPRITES_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` and `GITHUB_TOKEN` from it.
- A `factory` agent: `trailhead --as-me agent add factory`. The control plane acts as it, and each run gets a sub-agent (`factory/trail-42-a1`).
- To have merged PRs finish their tasks: `GITHUB_TOKEN` in the control plane's environment (read access to the repo's pull requests is enough), and the factory agent added to the project's reviewers, `trailhead --as-me project edit TRAIL --reviewers factory`, since only a reviewer can finish a task in review. Without the token the control plane logs a warning at start and merges aren't noticed.
- `.trailhead.toml` at the repo root, with the factory's settings under `[factory]` (the top-level `project` is shared with the CLI; `owner` and `name` default to the git remote): the repo, the queue task, checks, egress, profiles and budgets, and `max_sandboxes`.
- The local Trailhead server running (`trailhead server status`); the CLI starts it on demand.

## Starting and stopping

- **The daemon.** The control plane uploads a `trailhead-daemon` to each sandbox. It downloads the release asset matching its own version (`trailhead-daemon-vX.Y.Z-x86_64-unknown-linux-musl`, a static build the release workflow attaches with a `.sha256`) once, checks the checksum, and caches both in `<data dir>/factory/daemon/`; later starts re-check the cache against the checksum and download nothing. A checksum mismatch or a failed download stops the start; a mismatched binary is never cached or uploaded. Only the control plane reaches GitHub for this, so sandboxes need no extra egress. The order is: `--daemon <path>`, then a `trailhead-daemon` next to the `trailhead-factory` binary or on PATH (what `cargo install` leaves), then the release asset. A local daemon beats the release so a dev build whose version wasn't bumped never uploads an older release daemon over its own fresh one (a protocol mismatch). The log says which was used. With none of them (no local daemon and no release asset for this version) the start fails with a message naming `--daemon`.
- **Installed.** From the repo:

  ```sh
  cargo install --locked --path crates/trailhead
  cargo install --locked --path crates/trailhead-factory-host
  cargo install --locked --path crates/trailhead-daemon
  ```

  Then `trailhead factory run` from anywhere in the repo runs the installed `trailhead-factory` with the same arguments (`check`, `--poll-secs`, ...), looking next to the `trailhead` executable first, then on PATH, like `cargo foo` runs `cargo-foo`. `--config` defaults to the nearest `.trailhead.toml` at or above the working directory, and secrets still come from the environment (`fnox exec -- trailhead factory run`) until `factory login` (TRAIL-117). **A reinstall needs a factory restart**: a running control plane keeps running the old binary. Drain with one Ctrl-C (below), then start again.
- `mise run factory` builds the daemon and the control plane in release mode and runs it in the foreground. Its output is the log.
- `trailhead factory check` (under `fnox exec --`) reports what it can see without running anything: queued tasks, Sprites, its iroh endpoint. Stop `run` first; they share the lock below.
- **To restart without losing work, Ctrl-C once and wait.** The first Ctrl-C drains: it starts no new runs, reworks or reviews, lets the runs in flight finish as usual (including the review a finished worker run starts), logs `draining: N runs in flight (TRAIL-n, ...); Ctrl-C again to cancel them`, and exits 0 when none are left. Reconcile keeps running during a drain, but anything it finds due waits for the next start. Then start the new build. Only SIGINT drains for now; SIGTERM and a `stop` command come with the service (TRAIL-112).
- A second Ctrl-C stops it at once. Runs in flight are cancelled first (up to 15 seconds), and the next start's reconcile requeues their tasks (a run the control plane merely crashed on is followed again instead, if its daemon still has it) and returns their pooled Sprites to idle. Restarting is always safe, though a cancelled run counts as an attempt (TRAIL-159).
- The factory clones from GitHub, not your checkout: push `main` before queuing work that builds on local commits.
- One control plane per machine, whatever repo it runs: they share an iroh identity and would undo each other's runs. `run` and `check` take an exclusive lock on `<data dir>/factory/control.lock` before touching anything, and a second one fails with `a control plane is already running on this machine (pid N, running owner/repo, …)`. The lock goes when the process exits, even after a crash, so stop the running one first; `check` can't run beside it.

Local sandboxes on Docker instead of Sprites (`docs/factory/sandbox.md#docker`): `mise run docker-up` and `mise run docker-image` once, `[factory.compute] kind = "docker"` in the factory file, and the control plane built with `--features docker` and run with `DOCKER_HOST` set to the VM's socket. Until TRAIL-174 and TRAIL-175 land, Docker sandboxes have unfiltered egress and can't publish to GitHub, so this is for trying it out, not for real runs.

## Handing it work

- The factory only takes ready subtasks of the queue task (`[factory.repo] queue` in `.trailhead.toml`, TRAIL-102), highest priority first, up to `max_sandboxes` at once. Putting a task under the queue and **grading** it is the approval: there's no separate "go".
- **Grade it, or it isn't queued.** The factory works only graded tasks under the queue (grade 1 to 4, [review.md](review.md#grades)). An ungraded one is skipped: the log says so once, and so does a note on the task (`no grade; set one to queue it`), not on every poll. Set the grade to release it: `trailhead --as-me edit TRAIL-n --grade 2` (or `add ... --grade 2`). Only a person sets the first grade; the factory can raise it afterwards and never lowers it. Pick the grade for the risk you expect: 1 for docs and tests, 2 for ordinary code, 3 for dependencies, schema or public API, 4 for auth, secrets, egress, CI or the factory's own policy. A task that should never be the factory's work, like a shopping list item, just stays ungraded.
- **The PR can be graded higher than the task.** Before each review the control plane lists the PR's files and takes the highest of the task's grade, the `[factory.grades]` path rules in `.trailhead.toml` that any changed file matches, and grade 3 for a diff over `max_lines`. Deleting or renaming a test, or editing a check's definition (`.trailhead.toml`, `mise.toml`, CI workflows), is at least grade 2. The reviewer can also name a higher grade in its verdict. When the result is above the task's grade, the task is raised to it, with a note (`Raised to grade 3 (task was 1): Cargo.lock changed`), and the grade with what raised it goes in the task's `factory` metadata (`grade`). The reviewer's PR comment ends with it: `Grade 3 (task was 1; Cargo.lock changed)`. To override a raise you disagree with, lower the task's grade yourself.
- **Gates and shadow mode.** `[factory.gates.N]` in `.trailhead.toml` says what a PR of grade N needs before the control plane moves its task to `approved`: any of `checks` (the worker's checks passed, which is why a PR exists), `ci` (the repo's CI on the PR's current head: GitHub check runs and commit statuses, so the token needs read access to checks and commit statuses; a commit with none reported yet is pending), `agent_review` (the latest review verdict, on that head, approves) and `human` (you approved the task, `trailhead --as-me approve TRAIL-n`). `auto_merge` says whether the grade may merge on its own in `on` mode. Without a `[factory.gates.N]` the defaults of [review.md](review.md#grades) apply. `[factory.merge] mode` is `off` (the default), `shadow` or `on`; `on` turns the merger on (below). The gates are checked on the PR's current head after each review and on every reconcile pass, and a push after an approval sends the task back to `in_review` for a new one. The decision is kept in the task's `factory` metadata as `merge` (grade, gates passed, waiting on, would merge). In `shadow` mode the control plane also comments on the PR whenever the decision changes, once per change, never merging: `Grade 1: checks, CI and review passed; would merge (shadow).`, `Grade 1: waiting for CI.`, `Grade 1: CI failed (lint, test).`, `Grade 3 (task was 1; Cargo.lock changed): waiting for Lane.` Lane merges as usual and compares what it said; the merge finishes the task. With `off` it approves and records but doesn't comment. It can only move a task to `approved` if it's a project reviewer (the setup above); if not, the comment and a note on the task say so and it only records the decision.
- **Merging (`[merge] mode = "on"`).** An `approved` task whose grade has `auto_merge`, or that you approved, is squash-merged by the control plane (`CodeHost::merge`) and closed as `done` through the same function as a merge by hand, as the factory's identity; the handoff names the PR, the merge commit, the grade and the gates that passed. A PR behind `main` is first brought up to date (`update_branch`) and merged on a later pass once CI is green on the new head. The merge names the head the gates passed on, so a push that lands in between isn't merged. A merge conflict sends the task back to running for a rework on top of `main` (it costs a review round); a moved head, or a merge GitHub refuses for another reason (a required check, the branch rules), is logged and tried again on the next pass. The merger never force-merges. If the factory isn't a project reviewer it can't approve, so it falls back to shadow behaviour: the PR comment and a note on the task say why, and Lane merges. The mode is re-read from `.trailhead.toml` before each merge decision, so setting it to `off` (or `shadow`) stops the merger on the next pass without a restart; a file that can't be read or parsed keeps the last mode and is logged. Only `[merge] mode` is live: every other setting still needs a restart. Status: built (TRAIL-205); checked on fakes only, not on a live scratch repo, since none exists. Known gap: the update-branch commit is a new head, so the task goes back to review once per update rather than keeping the verdict (review.md's "verdict survives a clean update" isn't built).
- Create work there: `trailhead --as-me add "title" -p TRAIL --parent TRAIL-102 -P 2 -d "spec"`. To move an existing task in, `trailhead --as-me edit TRAIL-n --parent TRAIL-102`; `--parent none` takes it back out.
- Write the spec as you would for a careful contractor: which files, acceptance criteria, what not to touch, how to check it. TRAIL-105 is a good example.
- **The agent sees only the title and description.** Comments, including `decision` comments, don't reach it, so fold any decision into the description before queuing.
- **Keep queued tasks from colliding.** Each run branches from `main` as it is when the run starts, and PRs wait for you to merge, so two queued tasks that edit the same files produce conflicting PRs. Chain them with `trailhead block TRAIL-a TRAIL-b`: the second waits until the first is done, which is when you merge it.
- To take work back: `trailhead --as-me edit TRAIL-n -s cancelled`.

## Watching a run

The log shows, per task:

```
preparing a worker sandbox task=TRAIL-105 run=trail-105-a6
starting worker task=TRAIL-105 run=trail-105-a6 sandbox=trailhead-w1
step task=TRAIL-105 step=7 spent=$0.0412
tool task=TRAIL-105 tool=Bash detail=cargo test -p trailhead-daemon
run finished task=TRAIL-105 outcome=…
```

- `trailhead show TRAIL-n` shows the status, the claim (`factory/trail-n-aK` while running, renewed as it goes), notes and questions. The `factory` metadata holds the attempt, the pooled Sprite (`host`), spend and the PR.
- `trailhead watch` streams changes.
- To chase connection drops, set `[factory.daemon] log = "info,iroh=debug"` in `.trailhead.toml` (any `tracing` filter). Each daemon then starts with `--log <filter>`; without it they keep their default. It applies to daemons started after a restart of the factory. If the sandbox image sets `RUST_LOG`, that wins and `[daemon] log` is ignored; leave `RUST_LOG` unset in the image.
- A Sandbox's own daemon log is in the Sprites API for now (`/v1/sprites/<name>/services/trailhead-daemon/logs`); `trailhead factory logs` is TRAIL-109.

## What happens to a task

| Outcome | What you see | What you do |
| --- | --- | --- |
| PR opened | Task `in_review`, a PR on GitHub titled as a conventional commit with the task key last (`fix(factory): send the prompt on stdin [TRAIL-226]`; `chore: {task title} [TRAIL-n]` if the agent gave none), which is what the changelog picks up, with the reviewer's comment, a typed verdict on the task | Check CI is green and the diff's size is believable, and merge on GitHub |
| PR merged | Within a poll (`--poll-secs`, default 30 s) the task is `done`, with a handoff naming the PR and the merge commit, and `merged` (who, PR, commit) in its `factory` metadata. Tasks chained behind it unblock | Nothing. If `GITHUB_TOKEN` isn't set, or the factory isn't a project reviewer, finish it yourself: `trailhead --as-me done TRAIL-n -m "merged"` |
| PR conflicts with `main` | The task is reopened and reworked with `main` merged in, then reviewed again; conflict reworks have their own count, not review rounds; past `max_conflict_reworks` (`[repo]`, default 5) it is `needs_input` | Nothing, unless parked: merge `main` into the PR yourself, then reopen the task |
| PR closed without merging | The task is `needs_input` with a question naming the PR | Abandoned: cancel the task. To carry on, reopen the PR on GitHub, then reopen the task; the next run continues on the PR's branch |
| Reviewer approved with follow-ups | The PR comment ends with a "Follow-ups filed in Trailhead" list; each is a new open task in the project, not queued under TRAIL-102, whose description says which task and PR it came from. A title that's already an open task is listed as "(already open)" and not filed again. A request for changes files nothing | Triage them: queue the ones worth doing under TRAIL-102, cancel the rest |
| Reviewer requested changes | The review is posted on the PR and kept in the task's metadata; the task is open again and the next run starts from the PR branch head with the review in its prompt | Usually nothing. After `max_review_rounds` (`[repo]`, default 3) rounds the task is parked with a question holding the last review; fix the PR or settle it, then reopen (the count starts again) |
| Checks failed | A note on the task with the end of the failing check's output; the task is open again and retried | Usually nothing. The next attempt is told what failed; after `max_attempts` (`[repo]`, default 3) failures in a row the task is parked with a question summarizing the failure. Reopening does not reset the count, which runs from `attempt_base`; first run `trailhead edit TRAIL-n --meta factory.attempt_base=N`, where N is the task's current `factory.attempt` (see `trailhead show`). Never clear `factory.attempt`: it numbers the run, its sandbox and its reviewers, so renumbering collides with names already used. On a rework, the count starts from the review that asked for changes |
| Infrastructure failed (compute API error, wake failure, daemon lost without reattaching, git fetch timeout, or Claude Code's own API timeout, no response, overload or 5xx) | The attempt does not count toward `max_attempts`, and the run name's attempt number counts only attempts that did. The task goes back to the queue after a backoff of 1 min, doubling up to 15 min, per task. The failures in a row are counted separately (`infra_failures` in the `factory` metadata); at `max_infra_failures` (`[repo]`, default 10) the task is parked with a question saying it was the infrastructure, not the task, with the last error. An agent that ends a run resets the count. A reviewer that fails on the infrastructure is treated the same way: its review round is given back (it doesn't count toward `max_review_rounds`), the task waits out the same backoff before reconcile reviews it again, and at `max_infra_failures` it is parked with a question saying the infrastructure failed while reviewing the PR. That reviewer count is only in memory, so a control-plane restart starts it again at zero | Fix the host, the daemon or the API; nothing to do on the task unless it's parked, then reopen it (the count starts again; if it was parked after reviewer failures, reopening starts a worker rework on the PR branch before the next review; its sandbox, if it had one, stays for inspection and counts against `max_sandboxes` until you reopen it; the run loop then releases it before the next start, with no restart). A deliberate stop of the control plane does not count an attempt either. The agent giving up for other reasons, failed checks and a budget breach still count |
| Question | Task `needs_input` with a question comment; its Sprite stays busy | Answer it and set the task open. The run loop frees its sandbox on the next poll and starts a new attempt with the answer in its prompt; no restart |
| Budget or time breach | As a question, saying which limit it hit | Raise the budget in `.trailhead.toml` (restart the factory to load it) and reopen the task, or cancel it |
| Usage window nearly full | `subscription usage window nearly full; starting no new runs until it resets`, with how long until the reset | Nothing; runs start again at the reset. Change `[factory.usage] pause_at` in `.trailhead.toml` to leave more or less room |
| Dropped model call | `claude's API call failed; resuming the session` in the log | Nothing; it resumes up to three times |

## Sandboxes and cost

- Workers run in a lazy pool of warm Sprites (`trailhead-w1`, …, up to `max_sandboxes`). The first task pays a cold build of the repo (about 12 minutes for Trailhead today; TRAIL-120 should cut it). After that, each task restores the warm checkpoint and builds incrementally, in about a minute.
- Between tasks, pooled Sprites are restored (wiping the last task), have no egress and no connector access, and pause about two minutes after their last task. A paused Sprite costs only storage. Stopping the factory doesn't delete the pool; destroy a Sprite in the Sprites dashboard if you want it gone. A Sprite that keeps failing to release is given up on after five tries or ten minutes: an `ERROR` line in the log, the label `state=broken`, and a new Sprite for the next task. Destroy it in the dashboard if the factory can't.
- Reviewers get a fresh Sprite each, skip the build, and are destroyed after.
- Each run is capped by its profile's budget: dollars (API-equivalent in subscription mode), minutes and steps.

## Known rough edges

- No `status` or `logs` commands (TRAIL-109).
- New work is noticed on the next poll, not immediately (TRAIL-158).
- Reviewers try to build and can't, wasting time (TRAIL-136).
- A pooled Sprite has 8 GB and no swap; heavy builds have restarted one mid-run (TRAIL-140).
- No notifications (TRAIL-111); runs in a terminal rather than as a service (TRAIL-112).
- The GitHub connector has classic `repo` scope on all of Lane's repos and lets every Sprite use it (TRAIL-95).
